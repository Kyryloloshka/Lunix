# T-017 · Цифри не брешуть

## Навіщо (людською мовою)
Гравець ухвалює рішення за цифрами, тож цифри мають бути правдою.
- У HUD «+$X/с» показує лише пасивний дохід. Активний гравець заробляє тапами в рази більше, але
  бачить меншу цифру, і тапання відчувається марним.
- Картка навички обіцяє «+$3/с», а після купленого апгрейда ×3 насправді дає +$9/с. Картка множник
  ігнорує. Кава дає бонус до тапу, але рядок приросту в неї порожній.
- Ніде не видно, скільки **вже** дає кожна навичка, тож неясно, що качати далі і чи окупився апгрейд.

## Що бачимо зараз
- `HeaderHud.tsx` показує `rates.capitalPerSec`, тобто лише навички, без тапів, Flow і стресу.
- `SkillsCatalog.tsx` (рядок приросту) рахує `skill.capitalPerLevel × levels` без множників апгрейдів
  з `calculateSkillEffects` (`skillEffects.ts`) і без `clickCapitalPerLevel`.
- Ціни апгрейдів завжди форматуються як `$`, навіть для апгрейдів за іншою валютою (`SkillsCatalog.tsx`).

## Що зробити
1. **Реальний дохід у HUD:** модель веде ковзне середнє заробленого за останні ~5 с з усіх джерел
   (тапи, пасив, Flow, стрес) на основі таймстемпів, у фоні не рахує. HUD показує його основною
   цифрою, а пасив — дрібно під нею («пасивно $X/с»). Окремо для кожного відкритого ресурсу.
2. **Приріст на картці** рахує та сама функція моделі, що й реальні rates:
   `previewSkillGain(state, skillId, levels)` = rates після покупки − rates зараз. Це автоматично
   враховує апгрейди, пороги рівнів (25/50/100…) і майбутні множники. Перки показують свій ефект
   («−3% стресу за тап», «+$2 за тап»).
3. **Внесок навички:** на картці «дає зараз: $X/с · 34% доходу». Функція моделі
   `getSkillContribution(state, skillId)`.
4. Ціна у своїй валюті з правильним гліфом (Capital / Cognitive / Influence).
5. Картка апгрейда показує конкретно: «Async: $9/с → $27/с».

## Критерії готовності
- [x] Цифра в HUD при активному тапанні ≈ фактичний приріст балансу за 5 с (тест на модель з фейковим часом).
- [x] Приріст на картці дорівнює фактичній зміні rates після покупки — тест для кожної навички, з
  апгрейдами і без.
- [x] Кожна картка показує непорожній ефект.
- [x] Значення > 1e308 не дають NaN (Decimal, без `toNumber()` для відсотків внеску).
- [x] ts:check, test, web export пройшли.

## Поза скоупом
Перерозподіл ресурсів по навичках (це T-016). Зміна вигляду картки (T-004 етап 2).

## Де в коді
`entities/skill/model/skillEffects.ts`, `entities/currency` (ковзний дохід), `widgets/{header-hud,skills-catalog}`.

## Ризики і відкриті питання
Після T-016 у навички один ресурс, тож картка спрощується. Функції моделі писати під загальний
випадок `resource`, щоб не переписувати двічі. Порядок: після етапу 2 T-016 (рушій) або одразу на
поточній моделі, але через ті самі функції `previewSkillGain`/`getSkillContribution`.

## Результат
- `entities/currency/model/income.ts`: чисте ковзне вікно 5 с (`recordIncome`, `getIncomePerSec`), розрив > 2 с (фон) скидає вікно;
  офлайн-нарахування й нагороди не враховуються. Стор тримає `income` (runtime, не зберігається).
- `features/purchase-skill/model/skillIncome.ts`: `calculateRates` (єдина функція rates, нею ж синхронізується стор),
  `previewSkillGain`, `getSkillContribution`, `previewUpgrade`, `decimalShare` (частка через Decimal.divide).
- HUD: головна цифра = реальний дохід, під нею «пасивно X/с». Картки: приріст з апгрейдами/порогами, «дає зараз X/с · N% доходу»,
  ефект перків («+X за тап», «−N% стресу»), апгрейд «Навичка: A/с → B/с». Ціни вже в своїй валюті з гліфом (T-004).
- Тести: `income.test.ts`, `skillIncome.test.ts`. T-003 може брати `previewSkillGain`/`state.income` для «~N с».
