# T-020 · Прогрес переживе збій

## Навіщо (людською мовою)
Для idle-гри втрата сейву = втрата гравця назавжди (PRD §9, ризик «критичний»). Зараз є один ключ в
AsyncStorage: якщо запис обірветься посередині або дані зіпсуються, гра почне з нуля. Плюс немає
способу перенести прогрес на інший телефон чи відновити після перевстановлення.

## Що бачимо зараз
- `src/application/persistence/gamePersistence.ts`: один ключ, черга записів, `resetProgress`.
- Битий сейв → нова гра (правильно за safe-code §1, але без шансу відновити).

## Що зробити
1. **Резервний слот:** кожен успішний запис іде в основний ключ, а попередня валідна версія —
   у резервний (ротація). Під час завантаження: основний битий → беремо резервний, гравцю показуємо
   тихе повідомлення «відновлено з резервної копії».
2. **Експорт / імпорт рядком** у налаштуваннях: сейв → base64-рядок з версією і контрольною сумою;
   імпорт валідує так само суворо, як завантаження (safe-code §1), показує ранг/баланс до
   підтвердження, перезаписує через persistence (не з віджета).
3. Копіювання в буфер — `expo-clipboard` **після погодження**; без нього — поле з текстом для
   ручного виділення.
4. Тести: ротація слотів, відновлення з резерву, битий/чужий/майбутній рядок імпорту, контрольна сума.

## Критерії готовності
- [ ] Зіпсований основний сейв відновлюється з резервного (тест).
- [ ] Експорт → імпорт на чистій грі дає ідентичний стан (тест round-trip).
- [ ] Некоректний рядок ніколи не застосовується частково.
- [ ] `npm run ts:check`, `npm test`, web export пройшли.

## Поза скоупом
Хмарний сейв (E20), кілька незалежних ігрових профілів (якщо користувач не попросить).

## Де в коді
`src/application/persistence/*`, `widgets/settings` (кнопки), i18n.

## Ризики і відкриті питання
- Якщо змінюється формат зберігання — `SAVE_VERSION`++ і міграція (див. карту перетинів про черговість).
- Рядок експорту містить лише ігрові дані, жодних персональних (safe-code §6).
